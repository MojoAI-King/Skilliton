Rules:
- Base plugins live under `packs/base/plugins/`. **A fork treats `packs/base/` as read-only** and adds its own packs beside it (`packs/<company>/plugins/<plugin>/`, created with `new-plugin` after `company init` names the fork), with one stated exception: `packs/base/plugins/workflow/templates/harness.md` is the company's instruction template and a fork may edit it (expect to reconcile that one file when taking upstream changes). That reduces conflicts when reviewing upstream proposals; it does not remove the need for company review.
- Plugin skills are namespaced by Claude Code (`/plugin:skill`), which separates plugin invocation names from personal skill names. Verify discovery and invocation on each supported client.
- Every plugin skill's `SKILL.md` frontmatter carries `name` (required for plugin skills) and `description`.
- Every plugin's `plugin.json` carries `version`. Installed copies only receive an update when that version changes, so **every change to a plugin bumps its version**.

## 2. Project config: `.skilliton/config.json`

One file at the repo root, one section per component. Every key is optional. The code contract is `packs/base/plugins/workflow/runtime/lib/config.mjs`; every reader resolves the project through its `resolveProject()`.

```json
{
  "prepare":    { "version": 2,
                  "artifacts": { "status": "docs/STATUS.md", "backlog": "docs/BACKLOG.md", "backlogArchive": "docs/BACKLOG_ARCHIVE.md", "roadmap": "docs/ROADMAP.md", "decisions": "DECISIONS.md", "lessons": "docs/LESSONS.md", "handoff": "docs/HANDOFF.md", "handoffArchive": "docs/HANDOFF_ARCHIVE.md", "maintain": "docs/MAINTAIN.md" },
                  "directories": { "tasks": "docs/tasks", "decisions": "docs/decisions", "lessons": "docs/lessons" },
                  "integrationBranches": ["main", "master"],
                  "requires": { "workflow": "0.3.0" } },
  "handoff":    { "file": "docs/HANDOFF.md", "maxBytes": 6000, "keepEarlier": 5 },
  "checkpoints":{ "stopReminder": true, "minMinutes": 20 },
  "security":   { "maxAgeDays": null },
  "maintain":   { "teamLessonsFile": null },
  "dispatch":   { "laneRoot": "../<repo-name>-lanes", "hotspots": [], "mainOnlyPaths": ["docs/", "DECISIONS.md"], "laneSetup": [], "laneTestCommand": null, "mainOnlyChecks": [], "maxItemsPerLane": 8, "minItemsForLanes": 6 },
  "guardrails": { "protectedBranches": ["main", "master"], "blockForcePush": true, "blockNoVerify": true, "blockSecretFiles": true, "protectRecords": true }
}
```

- `guardrails.protectRecords` (guardrails 0.6.0): the shell guard denies `rm`, `rmdir`, `mv` and `git rm` aimed at a `.skilliton` folder anywhere, and in a prepared project at the record files from `prepare.artifacts`, the entry folders from `prepare.directories`, `CLAUDE.md`, `AGENTS.md`, or a folder that holds any of them (so `rm -rf docs`, `rm -rf .` and `rm -rf *` at the root are denied); the managed block guard refuses a `Write`, `Edit` or `MultiEdit` that would leave `CLAUDE.md` or `AGENTS.md` without the block. Both read this one key; only `false` turns them off, and the session-start line says when it is off. The one sanctioned route out is `skilliton remove --apply`, run by a person (B61).
- **A rule turned off says so on the command it lets through** (guardrails 0.7.0, B50): when `blockForcePush`, `blockNoVerify`, `blockSecretFiles` or `protectRecords` is false and a command passes that the rule would have refused, the shell guard prints `{"systemMessage":"[guardrails] Let through only because \"<setting>\": false under guardrails in <config> turned that rule off; ..."}` and no permission decision. Claude Code 2.1.278 shows it as a notice, "PreToolUse:Bash says: ...", and runs the command (measured headless 2026-09-22); how the interactive extension displays it is for a person to see. Under Codex its display is unverified.

- `prepare.version` is the project **layout** version: `1` was the standalone prototype (copied runtime at `.skillgate/bin/security-evidence.mjs`, `skillgate:project` markers), `2` is the integrated layout under the earlier Skillgate names, and `3` is the integrated layout under the Skilliton names. Layouts 1 and 2 keep their configuration in the earlier `.skillgate/config.json`; only `migrate`, `status`, `doctor` and the hooks open such a project, and every other command refuses it with the migrate command. Both configuration files at once are refused. A version the runtime does not know is refused, never guessed.
- `prepare.artifacts`: each record role maps to one Markdown file. Without an entry, the first existing conventional path is adopted (`config.mjs` `ROLE_CANDIDATES`), else the first candidate is the default. Two roles on one file, a path through a symbolic or hard link, a path under `.skilliton/`, or an instruction file (`AGENTS.md`, `CLAUDE.md`, `README.md`, entry-folder READMEs) is refused.
- `handoff.file` stays compatible: it names the handoff record when `prepare.artifacts.handoff` is absent, and disagreement between the two is refused.
- `prepare.recordHeader` (workflow 0.22.0): the line every record Skilliton writes opens with, one line of at most 200 characters with no control characters, holding `{kind}` where the record kind goes (for example `> {kind}` for a host whose docs check wants that). The default `Kind: {kind}` writes exactly what earlier versions wrote; records written before a change keep working, because the readers match the configured form and the default one. From a field report where every new task record broke the host's own docs check.
- `prepare.requires` maps plugin names to the **minimum** package version the project needs. Installed runtime version, required version, and applied layout/migrations are reported separately (never merged into one "up to date").
- `prepare.integrationBranches`: branches where the shared handoff, status, backlog and indexes are written. Everywhere else, work is recorded in its task record.
- `prepare` writes `handoff.file` equal to `prepare.artifacts.handoff`, because the session-start handoff hook reads `handoff.file`.
- **Drafted dispatch fields (workflow 0.10.0):** `prepare` reads the repository through `runtime/lib/stack.mjs` and drafts three `dispatch` keys, each shown in the preview with its source and written by `--apply`: `laneTestCommand` from the first build file that declares a test command, in this order: `package.json` `scripts.test` (`npm test`), `scripts.verify` (`npm run verify`), `pyproject.toml` containing `[tool.pytest`, `pytest.ini` or `conftest.py` (`pytest`), `go.mod` (`go test ./...`), `Cargo.toml` (`cargo test`), a `Makefile` with a `test:` target (`make test`); a malformed `package.json` counts as absent, nothing is run; `laneRoot` as `../<repository folder name>-lanes`; `hotspots` as the paths changed in at least 10 percent of the last 200 commits outside `dispatch.mainOnlyPaths` (default `docs/`, `DECISIONS.md`), most frequent first, at most five, and only once the history holds at least 10 commits. A key already set to a non-null value is kept and listed as kept. When nothing is detected the preview and the summary say so and name the key to set by hand; a draft is what prepare read from the repository, to be reviewed before it is relied on.
- Environment overrides: `SKILLITON_TEAM_LESSONS` (maintain), `SKILLITON_AUTO_PREPARE=off` (no preparation at session start for one session, said in the block; section 11), `SKILLITON_GUARDRAILS=off` (turns the guardrails hook into a visible no-op for one session; it prints that it is off), `SKILLITON_GUARDRAILS_CLIENT=claude-code|codex` (overrides guardrails' client detection), `SKILLITON_TRUST_DIR` (release signers, default `~/.config/skilliton/trust`), `SKILLITON_BACKUPS` (backups of files outside a project's Git folder), `SKILLITON_DENYLIST` (the private name scan), `SKILLITON_SELF` (how help text names the command). A variable still set under an earlier `SKILLGATE_*` name is not read; the command line and the session start name it and its replacement (section 16).

## 3. Handoff file: `docs/HANDOFF.md`

- Starts with `# Handoff`, then `Kind: Living.`, then a section headed exactly `## RESUME HERE`.
- `RESUME HERE` starts with a `Written: <date and time>` line, read from the clock, then four labelled items: **State**, **Next**, **Blocked**, **Watch out**. `status` reports a Written time more than five minutes later than the machine's clock as a problem, because it cannot be compared with later changes.
- Older blocks go under `## Earlier` as `### <Written date>` (newest first, at most `handoff.keepEarlier`, 0 to 20, default five; workflow 0.21.0, B60), older still to `docs/HANDOFF_ARCHIVE.md` (`Kind: Reference.`). With 0 the handoff holds `RESUME HERE` only, which is how this repository is set.
- **Mechanical writer (workflow 0.9.0):** `skilliton checkpoint --handoff --state --next [--evidence] [--blocked] [--watch-out] --apply` on an integration branch. It writes `Written:` from the clock as `YYYY-MM-DD HH:MM <zone>` when the local zone abbreviation is one the reader's zone table knows and matches the machine's offset (EDT here, UTC on CI), else as ISO `...Z`; the State item is `<state>. Evidence: <evidence>.`; a fifth item **Git** carries `<branch> @ <short head>, <n> uncommitted`. Blocked and Watch out carry over from the previous note when not given (a placeholder never carries; the defaults are `nothing` and `nothing known`), and every carry-over is printed. The previous block moves to the top of `## Earlier` as `### <its Written text>`; entries beyond five move to the top of `docs/HANDOFF_ARCHIVE.md` below its header, and a missing archive is created from the record template. Text outside `RESUME HERE` and `Earlier` stays where it is. On any other branch the flag writes the task record's `## Handoff` section only and says so. `runtime/lib/handoff.mjs` holds the parser, renderer and rotation as pure functions; `scripts/handoff-write.test.mjs` pins them.
- **Freshness (workflow 0.11.1):** the note is stale when its Written time is older than the latest commit (unless no commit came after the one that last changed the handoff) or older than an uncommitted change other than the handoff and its archive. The Written line is printed to the minute while file times are milliseconds, and one checkpoint writes the handoff, then the task record, then the indexes, so a change modified within five seconds of the end of the Written minute counts as part of that write rather than as later work (`HANDOFF_WRITE_WINDOW_MS` in `lifecycle.mjs`; without it a run that straddles a minute boundary reports its own index write as newer than the note it just wrote).
- **Refusals, nothing written, exit 2:** the handoff's Written time is later than the machine's clock by more than five minutes (`WRITTEN_AHEAD_MS` in `lifecycle.mjs`, the same skew `status` reports); no `## RESUME HERE`; no `Written:` line; a Written value the zone table cannot read; and, on every checkpoint, a task record whose Updated is later than the clock by the same skew. The bound `scripts/living-docs.mjs --check` enforces on this repository is 24 lines and 4500 bytes for the block and five entries under Earlier (the owner's choice, 2026-09-18).
- Writers by hand: `/workflow:handoff` where `skilliton` is not found (the same layout), and `/workflow:maintain` only when the day's checkpoints left the block behind the git log, **on an integration branch only**. On any other branch they write the task record's `## Handoff` section instead (section 11). Reader: `session-start-handoff.sh`, which prints the `RESUME HERE` section only, bounded by `handoff.maxBytes`, and prints a one-line notice when the file or section is missing.

## 4. Harness block in `CLAUDE.md` and `AGENTS.md`

The instructions that tell the model when to use which skill. Managed by `skilliton harness`, rendered from `packs/base/plugins/workflow/templates/harness.md`. `skilliton prepare` and `skilliton migrate` obtain block text only from the same renderer (`core.mjs` `planHarnessFile`); nothing else writes managed instruction markers.

```
<!-- skilliton:harness:start v1 -->
... rendered template ...
<!-- skilliton:harness:end -->
```

- Exactly one block per file. Applying replaces the text between the markers and never touches anything outside them.
- The template may name project values as `{{key}}`; the keys are `config.mjs` `templateVars()` (`status`, `backlog`, `backlogArchive`, `roadmap`, `decisions`, `lessons`, `handoff`, `handoffArchive`, `maintain`, `tasksDir`, `decisionsDir`, `lessonsDir`, `integrationBranches`). An unknown key is refused. Doctor compares a file's block with the template rendered for that project.
- The block labels every behavior as **enforced** (the installed, enabled hook handles its supported client event) or **instructed** (the model is asked to do it). Showing an existing handoff does not ensure one was written. Nothing instructed is described as guaranteed.
- `CLAUDE.md` and `AGENTS.md` receive the same block. Hook execution and skill invocation still need client-specific adapters and proof; matching Markdown does not establish Codex parity.
- Template changes reach a project when `harness --apply` or a project migration runs, never silently on plugin update.
- **The managed block guard** (`guardrails/hooks/managed-block-guard.mjs`, PreToolUse on `Write`, `Edit` and `MultiEdit`, guardrails 0.6.0): in a prepared project, a write to `CLAUDE.md` or `AGENTS.md` at the repository root whose result would carry fewer than both markers is refused, with the reason naming `harness --apply` and `remove --apply`. A write that changes text inside the block is allowed (doctor reports the drift). It sees the assistant's own file-writing tool calls and cannot see a script writing through Bash; it fails open on input it does not recognize, a file with no block, an edit whose `old_string` does not occur, an instruction file below the root, and a repository with no configuration. `guardrails.protectRecords: false` turns it off with the shell rule (section 2).

## 5. Team settings: `templates/project-settings.json`

The file a company commits as `.claude/settings.json` in its product repos, to declare the company marketplace, automatic plugin updates, and enabled base plugins for Claude Code. Every writing command shows its change first, writes only with `--apply` (or its own explicit verb), backs up what it overwrites, and exits non-zero with a plain-English reason when it refuses.

**Exit codes, every command:** `0` complete; `1` attention (an evaluated state needs action: a required doctor check, missing or stale evidence, a pending migration, a tampered package); `2` invalid or refused (bad invocation or data; nothing was written); `3` operation failed (an internal error, or a write that failed; the output says what completed). Recording an unresolved assessment successfully is `0`: the recording succeeded, not the control. Neither a zero exit nor current evidence freshness is a compliance verdict.

## 7. Improvement and update authority

Upstream proposal -> company review and tested release -> installed package update -> separate versioned project reconciliation. Application changes continue through normal application review and delivery. Plugin updates do not silently alter historical decisions, completed work, human edits or the application's code.

A lesson can propose a changed skill, check or template. It needs a reproducible scenario and review before becoming a released company default. Company extensions remain beside the base; upstream changes are reviewed rather than automatically granted company authority. A downstream repository owns its actual records and approved applicability choices.

Changes to validation policy need review by the authority configured for that repository; the proposed change cannot certify its own weakening of checks.

## 9. Integration contract v1: runtime modules

Agreed 2026-09-16 by the integrating session and implemented by six lanes merged one at a time.

- **Command module:** `runtime/commands/<name>.mjs` exports `help` (string, printed for `--help`) and `async run(argv)` returning an exit code. Options are parsed with `core.mjs` `parseArgs(argv, { flags, options }, "<name>")`; a command that needs a repeatable option (`--source`, `--artifact`, `--evidence`, `--criteria`) collects those first. `Refused` means exit 2; other errors exit 3. A subcommand is the first plain argument.
- **Engines:** `runtime/lib/`: `config.mjs`, `core.mjs`, `prepare.mjs`, `project-files.mjs`, `prototype-v1.mjs`, `migrations.mjs`, `ids.mjs`, `records.mjs`, `tasks.mjs`, `handoff.mjs`, `journal.mjs`, `session-hooks.mjs`, `lifecycle.mjs`, `security.mjs`, `collectors.mjs`, `treehash.mjs`, `release.mjs`, `verify.mjs`, `trust.mjs`, `delivery.mjs`.
- **`--json`:** where offered (prepare, migrate, status, verify), stdout carries exactly one `{ "schema": "skilliton.result/1", "command", "result": "complete" | "attention" | "invalid" | "operation-failed", "summary", "details" }` object, including on refusal and failure. The exit code matches `result`.
- **Cross-lane functions:**
  - `migrations.mjs`: `MIGRATIONS` (the ordered layout migrations), `migrationById(id, project)` (a layout migration or an instructions refresh), `instructionsState(project)`, and `migrationState(project) -> { layoutVersion, target, pending: [{ id, from, to, summary }], applied: [receiptId], instructions: { id, templateSha12, outdated: [file], applied } | null }`.
  - `security.mjs`: `securitySummary(root) -> { available: true, catalogVersion, total, applicable, current, missing, stale, expired, invalid, gaps, needsHuman, undecided }` or `{ available: false, reason }`; never throws for missing evidence.
  - `tasks.mjs`: `currentTask(project, branch) -> { task | null, ambiguous: [ids], unreadable: [...] }`; `readTask(file)` adds `file`, `criteria`, `lastCheckpoint` and `sections` to the contract fields.
  - `journal.mjs`: `appendEvent(root, event)`, `lastEvents(root, n)` (an array that also carries `corrupt`, `path`, `exists`, `truncated`), `mergesSince(root, baseHead, { limit, timeoutMs }) -> { merges: [{ sha, shortSha, subject }], problem }` (the merge commits between a baseline commit and HEAD, at most `limit`, with `problem` naming why the range could not be read instead of throwing). Events may also carry `task`, `source`, `trigger`, `reason`, `git`, and for `dispatch-suggested` the numbers `items`, `listItems`, `sentenceItems` with the boolean `promptTruncated`. A plain `stop` event is never written; only `stop-reminded`.
  - `session-hooks.mjs`: the hooks' pure decisions, so a hook's rule can be tested without a client. `parseHookInput(text)`, `sessionStartBlock(report, opts)`, `evaluateStop(...)`, `stopReason({ decision, state, current, merges })`, `countPromptItems(prompt) -> { items, listItems, sentenceItems }`, `dispatchSuggestion(counts, threshold) -> string | null`.
- Commands that call another engine import it dynamically and report "not available in this build" when it is missing. Task, decision and lesson IDs (`YYYY-MM-DD-<slug>-<hex4>`) come only from `ids.mjs`: `newId(title, { date, fallback, hex })`, `isId(id)`, `slugify(title, fallback)`, `localDate(date)`; no other runtime module defines the pattern (scripts/records.test.mjs checks).

## 11. Records, tasks, checkpoints and lifecycle

- **Entry IDs:** `YYYY-MM-DD-<slug>-<hex4>`. Two entries with the same title on the same day on two branches collide with probability 1 in 65,536, and Git shows that as a merge conflict, never an overwrite.
- **Task record** (`docs/tasks/<id>.md`): the header bullets **ID**, **State**, **Branch**, **Owner**, **Updated**, then `## Request`, `## Acceptance criteria`, `## Decisions`, `## Checkpoints`, `## Handoff`. Each checkpoint is `### <ISO time>`, a blank line, and four bullets: **State**, **Evidence** (`none given` when absent), **Next**, **Git** (`<branch> @ <short head>, <n> uncommitted`). Placeholders read `not yet written`. `dispatch --apply` writes one of these per lane inside the lane worktree and commits it on the lane branch (section 17), so a lane never runs `task start` for a scope the plan already fixed.
- **Commands:** `task start "<title>" [--request "<one line>"] [--criteria ...] [--branch] [--owner] [--dir] [--apply]` (state `in-progress`, owner `unassigned`, branch the checked-out one; a detached HEAD needs `--branch`; `--request` fills `## Request` with what the user asked for, in their words, and without it the section keeps its placeholder); `task list [--all]`; `task show [<id>]`; `task close <id> --state done-local|merged|released|verified|abandoned [--apply]`; `checkpoint [--task <id>] --state --next [--evidence] [--blocked] [--watch-out] [--handoff] [--dir] [--apply]` (writes the checkpoint and the task record's `## Handoff` four bullets in one write, then on an integration branch the indexes as `index --apply` would, with the shared handoff first when `--handoff` is given, section 3; off an integration branch or in an unprepared repository the index step prints that it is skipped and why). The current task is the open task whose Branch is the checked-out branch; more than one is reported as ambiguous, never picked.
- **A task that has grown past its start (workflow 0.22.0):** when the task holds 15 or more checkpoints, or its first checkpoint is more than 24 hours old, `checkpoint` prints one `checkpoint: note:` line suggesting the work be closed and a new task started; the note is never written into the record and never changes the exit code.
- **Decision and lesson entries:** `record decision|lesson "<title>" [--dir] [--apply]`, with the sections listed in the templates; Status is `proposed` off an integration branch, else `accepted`.
- **Indexes:** `index [--dir] [--apply]` regenerates the managed sections deterministically; `--apply` refuses off an integration branch; text outside the markers never changes; rerunning after a merge resolves an index conflict. A record without markers (an adopted one) gets its section appended only when there is something to list; until then it is left as it is.
- **The open-tasks index and the sessions check (workflow 0.22.0):** the open-tasks table carries ID, title, state, branch and owner, and no Updated column (the task record keeps the time), so a checkpoint rewrites the status record only when a task is added, renamed, or changes state, branch or owner; checkpoints still write the indexes (decision 2026-09-19-records-are-written-at-checkpoint-time-m-554d). The sessions check reads a previous session with no session-end whose newest session-start or stop is within 30 minutes as **live** (a note, blocking nothing: "another session looks active in this checkout (last seen ...), or it was interrupted: if it is open in another window, work in a worktree lane or check before committing shared records"; within 30 minutes the two cannot be told apart), and an older one as **interrupted**, as before.
- **Status:** `status [--dir] [--json]`: one line per check (layout, migrations, versions, enrollment, records, tasks, handoff, sessions, security) and a summary. `enrollment` (workflow 0.15.0) compares the plugin ids this project's `.claude/settings.json` sets to `true` against the ids in Claude Code's own `~/.claude/plugins/installed_plugins.json`, and is what says enrollment comes first when a session starts on a machine whose plugins are absent: a plugin's own hook cannot report that, because a missing plugin has no hook to run. It names the file it read and says that Codex records its installs elsewhere and is not read; an install record that cannot be read as Claude Code's shape is `not-run`, never a clean bill; and the ok line says that an installed plugin is not a hook that ran. Exit `1` for attention (a pending migration, an unmet required version, missing records, a stale handoff, or one whose Written time is later than now, on an integration branch, an interrupted session with uncommitted changes, unreadable or ambiguous tasks, security attention); a check that is "not run" (an absent module) does not change the exit code; `3` when a check could not be evaluated.
- **Hooks** (`"${CLAUDE_PLUGIN_ROOT}"/bin/skilliton hook <event>`, timeout 15 seconds, except `user-prompt-submit` at 10 because a prompt waits for it; the handoff hook stays first in `hooks.json`):
  - `session-start`: a "Project state" block bounded by `handoff.maxBytes` (current task, task handoff, previous session, shared handoff first, then layout, migrations, versions, enrollment, records, security), and a journal event. **Auto-prepare (workflow 0.18.0, `lib/auto-prepare.mjs`):** on a machine that has joined a company (a receipt under `~/.config/skilliton/joined/`), a repository with no `.skilliton/config.json` is prepared before the state is read: the same plan and transaction as `prepare --apply`, the files left uncommitted, and the block's first note says what was written and why; a prepared project is never touched again. It stays out, and the note says which: the receipt carries `"prepare": "offer"` (from the join file; the offer stands), an empty `.skilliton-off` file is at the repository root or a `skilliton-off` file is inside the Git folder (left as it is, and no offer is made), `SKILLITON_AUTO_PREPARE=off` is set (the offer stands), the project needs a migration (the migration line stands), or the machine has not joined (the offer stands). A failed write is rolled back like any `prepare --apply` and named with the command to run by hand. A prepared project with a pending instruction migration (kind `instructions`, the managed block behind the template) gets it applied under the same conditions (workflow 0.19.0), one at a time through the migration engine, receipt included, left uncommitted and named in the block; a migration that moves files is named with the command and not applied. A missing record is named with the command that brings it back (workflow 0.16.0, `lib/records-restore.mjs`): one Git tracks was removed from the working tree by hand, `git checkout -- <paths>`; one Git does not track was never made, `prepare --apply`; and when `.skilliton/config.json` itself is tracked but missing, the layout line names the removal with `git checkout -- <the tracked files that are missing>` and `remove --apply` as the route that records it on purpose, in place of the offer to prepare. `status` says the same in its records and layout lines. No hook restores anything (B61). An internal failure prints one notice line on stdout (the stream the client adds to context) and exits 0.
  - `stop`: blocks once per working tree state, measured from the later of the last checkpoint and this session's first start, after `checkpoints.minMinutes`, never when `stop_hook_active` is true, and never in a repository that is not prepared (workflow 0.18.0: nothing to checkpoint into, and the session-start block already said so); **and, on an integration branch, blocks when maintenance is due** (workflow 0.19.0, `lib/maintain.mjs`): a merge commit landed since the last `maintain` journal event, or (workflow 0.22.0) 15 commits landed since it, or a day and at least one commit passed since it, measured from the journal's first session start when there has never been one, or (workflow 0.22.0) the shared handoff was last committed 15 or more commits before HEAD, which a `maintain` event does not clear; asked once per commit (a `maintain-reminded` event with that head), with a paragraph naming `maintain --apply` and the judgment half, alone or after the checkpoint reminder's text; **and, on any branch, blocks when this session's prompt named dispatch** (workflow 0.20.0, `evaluateDispatchHold` in `lib/session-hooks.mjs`): the session's last `dispatch-suggested` event is later than `LANES.md` at the repository root (or there is none), asked once per such prompt (a `dispatch-reminded` event carrying `suggestedAt`); the dispatch paragraph comes first, then maintenance, then the checkpoint reminder; `checkpoints.stopReminder: false` turns all three off; the reason names the exact command. When a merge commit landed in that same window the reason adds one sentence naming `/workflow:maintain`, and says so plainly when the range could not be read. A merge alone is enough to make the reminder due, because HEAD is part of the fingerprint. When the audit (section 14) finds anything in the files the working tree changed, the reason adds one sentence naming the count, the files and `skilliton audit`, and says plainly that this is a report and not a block; when the audit could not run, it says that instead of saying nothing. Because it shares the once-per-fingerprint rule, that sentence is said once per tree state, not on every stop. Failures print one line on stderr and allow.
  - `pre-compact`, `session-end`: journal events; session-end gives `git status` one second because Claude Code shares a short budget among SessionEnd hooks.
  - `user-prompt-submit`: reads the prompt from `prompt` (the field Claude Code 2.1.278 sends, measured 2026-09-22), else `user_prompt`; when it reads as `dispatch.minItemsForLanes` or more separate items, one note directing `/workflow:dispatch` before any code (workflow 0.20.0; it was a suggestion before) on stdout as `{"hookSpecificOutput":{"hookEventName":"UserPromptSubmit","additionalContext":"..."}}`, and a `dispatch-suggested` journal event. An item is a numbered line, a bulleted line, or a sentence opening with an imperative verb after any lead-in; fenced code is skipped. It is advice and never a block: it never exits 2, and because it runs on every prompt it prints nothing at all when the folder is not a Git repository or the count is below the threshold. Whether Claude Code delivers this event to a plugin hook is unverified here; the fixture tests prove the hook's own side.
- **`maintain [--dir] [--apply]`** (workflow 0.19.0): the mechanical half of maintenance: the indexes (as `index --apply`), the secrets and delivery-policy records when a register exists and either is missing or stale (as `security collect secrets` and `security collect delivery-policy`, reviewer `skilliton maintain`, workflow 0.22.0; never the tests collector, which runs the project's checks), the security findings block when a register exists (as `security findings --apply`), and a `maintain` journal event; refused (exit 2, nothing written) in a repository that is not prepared or off an integration branch. The judgment half stays with the maintain skill.
- **Interrupted session:** a `session-start` with no later `session-end` for the same session ID; the next session's Project state names it (measured live on Claude Code).

## 12. Project security evidence

- **Engine and command:** `runtime/lib/security.mjs` keeps the prototype's record schema 1, immutability and refusal of links and secret-shaped input. `security status|record|applicability|collect|findings`, each with `--dir`, preview by default, `--apply` to write. Status exits `0` only when every applicable control has a current observed record; `1` for missing, stale, expired, gap, needs-human or undecided; `2` for an invalid catalog, records or input (then `--apply` writes no report); `3` for failures.
- **Applicability:** `applicability.json` as agreed; newest decision per control wins; undecided counts as needs-human; `applies: false` leaves the denominator and is listed with its rationale. Concurrent writers take `applicability.lock`; a left-over lock refuses with instructions.
- **Proposed applicability (workflow 0.22.0):** `applicability --propose [--apply]` reads the tracked files (bounded like the secrets collector) and writes `.skilliton/security/applicability-proposal.json`, one entry per control with whether it looks applicable and the signal behind it; it decides nothing. `applicability --accept-proposal --decided-by <label> [--replace] --apply` records each entry as a decision with rationale "proposed from repository signals: <reason>", and refuses a missing proposal, one older than the files it read, and without `--replace` a control already decided by hand.
- **Freshness:** stale when a fingerprinted file changed or disappeared, the control or catalog version changed, or `maxAgeDays` passed (the control's own value wins over `security.maxAgeDays`). Scan evidence carries a file manifest; its files are re-verified by size, time and, when the time differs, content. Regenerating a report never creates or re-dates a record.
- **Collectors** (`security collect <name> [--control <id>] --apply`): `tests` runs the delivery policy's checks without a shell (default control `SG-SECURITY-TESTS`, requires `--source`, adds the policy file to its sources); `secrets` scans tracked files and records a **gap** only for specific shapes (private key block, provider token prefix, JSON web token) and **needs-human** when only generic shapes match (default control `SG-SECRETS-IN-SOURCE`); `delivery-policy` (default control `SG-CHECK-CRITERIA`). Artifacts go to `.skilliton/private-evidence/`, which other clones do not have, so there the record reads stale.
- **Scoped observation (`audit --record --apply`, workflow 0.14.0):** one record per control the rules cover, a **gap** when that control has findings and an **observation** when it does not, with the run's report attached and a manifest naming **exactly the files the audit read** as its sources. That is what keeps a clean audit from outliving the files behind it: the freshness rule above marks the record stale the moment one of those files changes. It needs the working tree, because that is what the register re-reads; with `--range` the run is reported and never recorded.
- **Secrets allowlist (workflow 0.22.0):** `.skilliton/security/secrets-allow.json`, a JSON array of entries `{path, rule, sha256, reason}`, where `sha256` is the hash of the matched line's bytes, which the report prints beside every match, and `reason` is required. An entry is bound to that content: `line` is refused, because a line number would allow whatever later lands on the line, a real key included (2026-09-23 review). A hit matching an entry by path, rule and line hash moves from the matches to an **Allowed** section of the report with its reason, never its text; the assessment is a gap only when an unallowed specific match remains; an entry that matched nothing is listed as unused. An invalid file refuses (`INVALID_SECRETS_ALLOWLIST`, exit 2) naming the entry index and field. The file's fingerprint is in the collector's file manifest, so editing it makes the record stale (decision 2026-09-23-n47-secrets-allowlist-freshness-folds-in-419c: a source whose name holds "secret" is refused as a sensitive path).
- **Refusals name the field (workflow 0.22.0):** `security record` says which of the control, assessment, note, reviewer, sources or artifacts it refused and which rule it broke, never the value. `security status`, and the `tests` and `delivery-policy` collectors, say when `.skilliton/delivery.json` is absent and name `skilliton delivery confirm --apply` when a draft exists.
- **Findings:** `security findings --apply` writes one row per applicable control that is not current, observed and decided, keyed `SEC-<id>`, sorted, idempotent; a resolved row leaves; a missing backlog record or invalid evidence refuses.
- **Catalogs:** `catalogs/index.json` names `skillgate-baseline-2` (15 controls, 36 related references to NIST SSDF 1.1 and OWASP ASVS 5.0.0, verified in docs/security-catalog-sources.md). Prepare copies it into new projects; an existing project keeps its catalog until a reviewed migration changes it.

## 13. Releases, verification and trust

- **Manifest** `releases/<version>.json`: the agreed fields plus `notes` (what could not be recorded, for example an absent migrations module) and `clients` (`{ catalog, marketplace, plugins }` per client, with a note when there is no Codex catalog). `release create` refuses any uncommitted, untracked, ignored or mode change under a component, a duplicate version, an escaping or linked component path, disagreeing versions, uncommitted evidence, and (when the release carries migrations) a runtime other than the release's own workflow plugin.
- **Approval and withdrawal:** `release sign <version> [--apply]` checks the manifest is committed and unchanged and every component still matches, requires SSH signing, then tags `skilliton-release/<version>` with `manifest-sha256: <hex>`. `release withdraw <version> --reason <text> [--apply]` tags `skilliton-withdrawn/<version>`. `release list [--company]` shows approved, unapproved and withdrawn; exit `2` when trust is missing or any tag does not check out.
- **Trust:** `trust add --company <name> --signers <file> [--apply]`, `trust show [--company]`, `trust remove --company <name> [--apply]`. A trusted tag must be annotated, name itself, point at a commit, carry one complete SSH signature verified with `ssh-keygen`, and name a principal from the signers file.
- **`verify [--client claude-code|codex] [--config-dir] [--source] [--company] [--json]`:** VERIFIED, TAMPERED (changed, added, missing or unreadable files named), UNKNOWN VERSION, WITHDRAWN, NOT INSTALLED. Exit `0` only when every company plugin is VERIFIED and every file its release marks executable is executable; `1` otherwise (including nothing installed, or a lost executable bit); `2` when trust is missing, the client's install records are malformed, or any release tag in the source does not verify (O19); `3` on failure. `--source` defaults to the skills repository the runtime runs from; from an installed copy, to the clone `join` recorded for `--company` (or for the only company joined), else it is required; a URL source is not built. For Codex without a Codex catalog, the marketplace name comes from `.claude-plugin/marketplace.json`, as a release manifest records it. The content hash does not cover the executable bit: a file the release marks executable that is not executable stays VERIFIED by content, is listed in the plugin line's `notRunnable`, and makes the exit `1`; a bit the release does not have is a note. Both clients kept every executable bit on a clean install (measured 2026-09-16). Claude Code install records and Codex cache folders are read as observed and labelled undocumented.
- **Joining a machine:** `join --from <join file>` (workflow 0.15.5), or `join --company <name> --signers <file> [--client all|claude-code|codex] [--marketplace <owner>/<repo>|<folder>] [--plugins <a,b>] [--bin-dir <folder> | --no-launcher] [--release <x.y.z> | --no-pin] [--claude <path>] [--codex <path>] [--repo <clone>] [--apply]` and `join --undo --company <name> [--claude <path>] [--codex <path>] [--apply]`. It runs from a full (not shallow) clone of the company skills repository, which becomes the verify source. For each client found it runs `claude plugin marketplace add <source>` and `claude plugin install <plugin>@<marketplace>`, or `codex plugin marketplace add <source> --json` and `codex plugin add <plugin>@<marketplace> --json`, creating a missing `CODEX_HOME` first (Codex refuses one that does not exist). `--marketplace` defaults to the team template's GitHub repository; plugins default to the template's enabled plugins and must include `workflow`. Trust uses the `trust add` checks. The launcher `<bin-dir>/skilliton` (default `~/.local/bin`) is a POSIX shell script that runs `node <clone>/scripts/skilliton.mjs`; on Windows (`process.platform` `win32`, injectable for tests through `SKILLITON_PLATFORM`) join also writes `<bin-dir>/skilliton.cmd` for PowerShell and the Command Prompt, CRLF, which checks that `node` is on PATH and runs the same script (content pinned by `scripts/join.test.mjs`; not yet run on Windows); a file already there that is not this company's launcher is never replaced, and no shell profile is edited. Install state is read from the clients' files, and a client binary runs only to make a change (every Codex invocation writes into its home), so a preview, a repeat with nothing to do, and a refusal run no client. Receipt `$SKILLITON_JOIN_DIR/<company>.json` (default `~/.config/skilliton/joined/`, mode 0600), rewritten through a temporary file after every change: `{ "schema": "skilliton.join/1", "company", "source", "joinedAt", "updatedAt", "marketplace": { "name", "kind": "github"|"directory", "location" }, "trust": { "path", "sha256" } | null, "clients": { "claude-code"|"codex": { "home", "marketplaceAdded", "installed": [], "createdHome"? } }, "launcher": { "path", "sha256", "createdFolder" } | null, "launcherCmd": { "path", "sha256", "createdFolder": false } | null }` (`launcherCmd` is absent in receipts written before 0.10.0 and null off Windows; a present value must name a file called `skilliton.cmd`). Undo requires each client home to be the one recorded; uninstalls the recorded plugins still installed; removes the marketplace when join added it and nothing else from it is installed; removes the signers file and the launchers (`skilliton.cmd` first, then `skilliton`) when their sha256 still matches (and the launcher folder if join created it and it is empty; a launcher changed after join is kept and named); backs up the signers file and the receipt, then deletes the receipt. Exit `0` complete and every plugin VERIFIED (undo: everything removed); `1` attention (a plugin not VERIFIED, the launcher not written, or undo kept something); `2` refused before any change; `3` a client command failed part way (the receipt records what completed).
- **The join file** (`skilliton.join/1`, workflow 0.15.5): `{ "schema": "skilliton.join/1", "company": "<name>", "repo": "<git URL of the fork>", "signers": "<allowed_signers text>", "prepare": "auto" | "offer" }` (`prepare` optional, workflow 0.18.0, written by `--prepare offer` and copied into the join receipt; absent means `auto`, and a receipt from before the field reads as `auto`), at most 64 KB, written by `company join-file --name <company> --signers <file> --out <path> [--repo-url <url>] [--apply]` (the URL defaults to the GitHub repository `templates/project-settings.json` names) and refused when `--out` is inside a Git working tree. `join --from <file>` refuses it with `--company` or `--signers`, validates the schema, the company name and the signers text before anything else, writes the signers to a private temporary file for the trust step, and removes that file when join ends. The join file travels the same out-of-band channel as the signers file: never the repository.
- **Pinning a clone to a release:** `pin [--release <x.y.z> | --latest] [--company <name>] [--repo <clone>] [--apply]` (workflow 0.15.0). A release is approved when its `skilliton-release/<version>` tag carries an SSH signature verifying against the company signers file, its signed first line is `skilliton release <version>`, it carries one `manifest-sha256: <64 hex>` line, and that hash matches the manifest blob at the approved commit. What is pinned is the clone the marketplace and the launcher point at, not a client's own download: `claude plugin marketplace add` takes no ref, tag or branch, and `marketplace update` takes none either (measured 2026-09-21), so a download is checked by `verify` rather than pinned. The pin follows the signature, not the ref: it checks out the commit the verified tag object names, never the tag name, which would follow wherever that ref points now. `--release` takes a plain `MAJOR.MINOR.PATCH` version and nothing else, so there is no spelling of a branch, a commit or a tag name that moves a clone. The record is `<git dir>/skilliton-pin.json` (mode 0600, written through a temporary file), `{ "schema": "skilliton.pin/1", "company", "version", "tag", "tagObject", "commit", "from", "seen": { "<version>": "<tag object id>" }, "pinnedAt" }`; it lives with the clone because a pin is a property of one clone and not of the machine, and `seen` carries every release tag the clone held when it was pinned. A later run refuses when any of those tag objects has changed or gone, which is how a rewritten tag is caught whichever version is being installed; a changed file that git tracks refuses too, because the clone would then not hold the release even at the right commit, while an untracked file is reported and allowed. `join` pins before it writes anything, to the newest approved release or to `--release`, decided against the signers file it is about to trust so a first join on a machine that trusts nothing yet still refuses an unsigned or moved tag; a newest release that is not approved refuses rather than quietly installing an older one, a clone with no release tags is joined unpinned with a note, and `--no-pin` joins the clone as it stands and says so. Pinning leaves a detached HEAD, which is what keeps the clone there. Exit `0` done or nothing to do; `1` the clone holds releases that do not verify; `2` refused with nothing changed; `3` git failed part way.
- **Machine checks before setup:** `preflight [--client all|claude-code|codex] [--marketplace <owner>/<repo>|<folder>] [--bin-dir <folder>] [--no-network] [--repo <clone>] [--wide] [--json]`. It changes nothing except one file named `.skilliton-preflight-<12 hex digits>` (mode 0600) that it writes and removes in each folder it tests, and a folder that does not exist yet, which it creates (mode 0700), tests and removes again; an interrupted run removes its own file. Programs come from the `PROGRAMS` table in `runtime/lib/preflight.mjs`, which `scripts/allowlist.test.mjs` holds equal to section 1 of docs/IT-ALLOWLIST.md: the ones hooks start are started by `runtime/preflight/probe.sh`, run by its path (the way Claude Code runs a hook), and the ones the runtime starts are started by node, each once with `--version`; a file on PATH that this user may not run is reported as blocked, not missing. A coding tool is never started (starting Codex writes into its home), so it is checked as a file. The repository check is the runtime's only command that contacts a remote: `git ls-remote --heads https://github.com/<owner>/<repo>` with `GIT_TERMINAL_PROMPT=0`; a folder marketplace is checked for its catalog instead. Each item is `ok`, `blocked`, `missing` or `not checked`, and carries what it stops: `setup` (join cannot finish) or `sessions` (a hook would not work). Exit `0` nothing in the way; `1` something is blocked or missing; `2` refused; `3` the check failed. `join` runs it first with the setup scope and refuses with exit `2`, before anything is written, when an item that would stop setup is not ok; items that would only stop a session are printed and do not stop it. A coding tool the caller named with `--claude` or `--codex` is checked at that path, not by its name on PATH.
- **Proposals:** `propose <lesson file> [--repo] [--apply]` writes `proposals/<lesson id>.md` after the scrub check and the secret-shape scan pass on the exact text.

## 14. Trusted delivery checks

- **Policy** `.skilliton/delivery.json` (schema `skilliton.delivery/1`): unknown keys refused; `policyPaths` must include `.skilliton/delivery.json`; a commit without it that still has the earlier `.skillgate/delivery.json` is governed by that file in its earlier format (schema `skillgate.delivery/1`, `policyPaths` covering its own path), so a shared branch stays protected until the project's migration commit moves the policy; every commit that touches either policy file needs an approver's signature, whichever file governs the branch, and because each commit is compared only with its first parent, the combined result is checked too: every policy path that differs between the current tip and the pushed tip must hold exactly the content an approver-signed commit in the push gave it, so a merge cannot bring back an earlier policy; check names 1 to 64 characters, unique; `timeoutSeconds` default 600, at most 86400; `checks: []` is valid and runs nothing.
- **Draft and confirm (workflow 0.10.0):** `prepare --apply` writes `.skilliton/delivery.draft.json` (same schema; `protectedBranches` the first integration branch; one check `tests` with the detected command's argv and `timeoutSeconds` 600; the default `policyPaths`) when it detected a test command and neither the policy nor the draft exists. No gate reads a draft: `gate` without a policy but with a draft refuses and names `delivery confirm`. `delivery confirm [--dir] [--apply]` previews the draft's checks, protected branches and policy paths, and `--apply` moves it to `.skilliton/delivery.json`; refused (exit 2, nothing written) when there is no draft, the policy exists, the draft is invalid (its problems listed), or plain arguments are given. The confirmed file is committed and signed like any other policy change.
- **The audit step (workflow 0.14.0):** the gate reads the files the push changed, at the pushed tip, with the same rules `skilliton audit` uses, and **a finding rejects the push**, named with its file, line, rule and control. It reads the whole of each changed file, not only the added lines, because the push is what you are answering for. A line that is meant to be there carries `skilliton-audit: allow <rule> <why it is allowed here>`. The policy field is `"audit": {"enabled": false}`, which turns it off; `.skilliton/delivery.json` is a `policyPaths` entry, so turning it off needs an approver's signature like any policy change. It is **on by default**, so a project that has never heard of it still gets the check, and the push that creates a protected branch is not audited, because there is no previous tip to compare with and auditing the whole tree would reject the push that installs the gate over code that was already there. A policy with no checks and the audit off says so and runs nothing.
- **The removal rule (workflow 0.16.0, `lib/delivery-persist.mjs`):** a push whose result removes a file Skilliton keeps in the project is rejected unless the commit that removes it (judged against its first parent, like a policy path) carries an approver's signature; the reason names the commit, the path and `skilliton remove --apply` as the route. What is kept: everything under `.skilliton/`, `CLAUDE.md`, `AGENTS.md`, the record files and the entry folders as the configuration at the current tip names them (`prepare.artifacts`, `prepare.directories`), with the defaults for every role it does not name. Adding or changing them is free; a removal no commit in the push makes on its own (a merge resolved by dropping the file) has no commit to sign for it and is rejected as such; without an approvers file the removal is reported as NOT CHECKED like a policy change. The earlier `.skillgate/` folder is not covered, so a migration commit that moves it is not held by this rule (the policy move already needs a signature).
- **Hardening (workflow 0.22.0):** every git call the gate makes sets `GIT_NO_REPLACE_OBJECTS=1`, and every update to a ref under `refs/replace/` is rejected, so a replace object cannot make the gate read a policy the branch does not hold; the gate fingerprints its pre-receive hook, its approvers file and its `skilliton.*` and `core.hooksPath` settings before the checks and after each protected update and rejects a push that changed any of them (`lib/delivery-integrity.mjs`); a commit counts as signed only when every signature header on it is SSH, with the OpenPGP and X.509 verifiers pointed at a program that does not exist.
- **Protected branches:** the policy on the bare repository's default branch lists them; while that branch has no policy, it alone is protected. Each protected branch is checked with the policy on its own current tip. An invalid default-branch policy rejects every push.
- **The gate** (`delivery install --bare <repo.git> --approvers <file> [--runtime <bin/skilliton>] [--apply]` writes a marked `pre-receive` hook that reads the runtime path from Git config at push time and fails closed): rejects non-fast-forward updates and deletions; reads the policy from the current tip; requires every pushed commit that changes a policy path, compared with its first parent, to carry an SSH signature from the approvers file (other signature types are rejected); creating a protected branch needs a signed tip that contains a valid policy; a push that removes or breaks the policy is rejected; extracts the pushed tip with `git archive`, compares every file with the commit, runs each check with a minimal environment in its own process group, and rejects naming the failing check with the last 20 output lines.
- **`delivery check [--repo] [--ref] [--remote] [--approvers <file>]`:** the same evaluation of the local HEAD against the remote-tracking tip; without an approvers file a needed signature check reports NOT CHECKED and exits 1.
- **Hosted adapter:** `templates/github/skilliton-delivery.yml` and docs/DELIVERY.md; documented, not rehearsed on a hosted repository (O15).
- Local assistant guardrails and security evidence freshness are never presented as merge enforcement.

## 17. Dispatch: lanes, worktrees and briefs

Built in workflow 0.11.0; `dispatch merge` and the lane's committed task record in 0.12.0. `dispatch [--file <plan>] [--dir <project>] [--preview] [--apply]` reads a lane plan and creates one Git worktree per lane. The engine is `runtime/lib/dispatch.mjs`; the skill that writes the plan is `skills/dispatch`.

**The plan.** `LANES.md` at the repository root by default, at most 200KB (a plan longer than that is refused, naming the size: a page per lane is the shape, and a runaway file is a mistake, not a batch). Three things are read and nothing else is inferred:

- `## Lane: <name>` starts a lane and runs to the next level-1 or level-2 heading, so a `### Brief` section stays inside it. The name and each field are separated by **two or more spaces**; a single space inside a field's value is ordinary. Known fields: `branch` (required), `model`, `context ceiling`. An unknown field, a missing branch, a duplicate lane name, a name that is not a folder name, or a branch that is not a branch name is a problem, and every problem in the plan is reported together before anything is created.
- `Base commit: <sha>` on its own line outside a lane sets the base for every lane below it (7 to 40 hexadecimal characters, optionally as a list item, bold, or in backticks). With no such line the plan uses `HEAD`, and the printed plan says which it used and where it came from. A base the repository does not have is refused.
- `N<k>. <text>` inside a lane is one item. A lane with no items is created with a brief that says the plan named none, rather than a guessed scope.

**What it refuses (exit 2, nothing created).** A missing plan; a plan with no lanes; a lane root inside the repository; a lane folder that exists, or one Git still has registered as a worktree; a lane branch that already exists; a repository with no commits; `--apply` with `--preview`; a plain argument. The whole batch is checked before the first worktree is made, because half a batch is worse than none.

**What it writes with `--apply`.** One worktree per lane, created with `git worktree add <laneRoot>/<name> -b <branch> <base>`; `LANE_BRIEF.md` at each worktree root; and `LANE_BRIEF.md` plus `LANE_REPORT.md` in the repository's `.git/info/exclude`, so a lane's brief and report are never committed. It never runs a `dispatch.laneSetup` command: those are printed and written into each brief for a person to run, because dispatch runs in repositories nobody has reviewed.

**The brief is the bound.** Each `LANE_BRIEF.md` carries the lane, its branch and base, its worktree, the integration branch, the model and context ceiling the heading named, the two checks to run before writing (branch and base ancestry), the lane's items and nothing else as its scope, a "Your bound" section (what to read, what to return, the model, the ceiling, and that nothing is silent), the main-only paths with the per-lane exception for its own task record and proposed entries, the launch line naming the shipped `lane` agent (section 18), the check to run, and the setup dispatch did not run.

**Lane root.** `dispatch.laneRoot` (section 2), or `../<repository folder name>-lanes` when unset, which is why dispatch resolves it rather than `config.mjs`. A lane root inside the repository is refused: a worktree under the repository would be walked by its own checks.

**The lane's task record.** `--apply` writes one task record per lane inside its worktree (section 11) and commits it on the lane branch alone as `lane <name>: task record from LANES.md`: State `in-progress`, Branch the lane branch, Request naming the plan and the dispatch date, and one acceptance criterion per item, each carrying its N number. It is committed rather than asked for in the brief, so a lane's scope is a file whether or not the session that reads the brief obliges, and `dispatch merge` has something deterministic to bring back. One commit on top of the base keeps the base an ancestor of the lane branch, which the brief's own check requires.

**Merging the lanes back.** `dispatch merge [--dir <project>] [--apply]` runs on the integration branch in the main checkout and is refused inside a linked worktree. It finds lanes from `git worktree list --porcelain`, keeps those under the lane root, and reads what each lane branch has **committed** under the task, decision and lesson directories (`git ls-tree`, then `git show`). A lane's working tree is never read, because the brief tells the lane to commit. Every file is one of three classes:

- **brought back:** absent from the integration branch's working tree. `--apply` writes it there and commits nothing, so the person reads `git status` and `git diff` and commits.
- **already here:** present and byte for byte identical. Counted, never written again.
- **conflict:** present and different, unreadable, not text, or claimed by two lanes with different content. Named in the report and never overwritten.

Two further states are reported without refusing: a lane with uncommitted changes, and a lane whose `LANE_REPORT.md` is missing, over 200KB, or has no `LANE DONE` line.

**Exit codes for merge.** `0` everything came back clean; `1` attention (a conflict, a lane with uncommitted changes, or a lane that has not written LANE DONE: the merge-back is incomplete either way, and reporting it as complete would be rounding up); `2` refused, nothing written; `3` a write failed, and the output names what was written before it.

**The lane write guard.** `guardrails/hooks/lane-write-guard.mjs` (PreToolUse on the file-writing tools) refuses a write to a main-only path from inside a lane worktree, with the lane's own task, decision and lesson directories as the exception the brief depends on. Its limit is part of the contract, because an unstated limit in a guard is worse than no guard: it sees the assistant's own file-writing tool calls and cannot intercept a script writing through Bash, so it bounds the assistant, not the worktree. Each refusal says so. It fails open on a payload it does not recognize, a folder that is not a repository, the main checkout, a repository with no Skilliton configuration, and a path outside the repository.

## 18. Agents shipped in a plugin

A plugin's `agents/<name>.md` files are discovered automatically; the `agents` key in `plugin.json` is optional (documented, retrieved 2026-09-20). Installed, they are named `<plugin>:<name>`.

Every agent Skilliton ships states `model` and `effort` in its frontmatter, and `scripts/packs.test.mjs` fails without them: an agent with no model runs on whatever model the calling session happened to be using, which makes cost and quality a property of when it was called rather than of what it does. The accepted values are the documented ones: `model` is `sonnet`, `opus`, `haiku`, `fable`, `inherit` or a `claude-` model id; `effort` is `low`, `medium`, `high`, `xhigh` or `max`; `maxTurns` is a positive integer. No documented frontmatter key sets a subagent's context window or its compaction, so a bound is written into the agent's instructions and into the lane brief, not configured.

| Agent | Model, effort | Reads | Returns |
|---|---|---|---|
| `workflow:lane` | sonnet, high, no turn limit | `LANE_BRIEF.md` in its worktree, the files its items name | `LANE_REPORT.md` with its five headings, ending `LANE DONE` |
| `workflow:locate` | sonnet, low, 12 turns, read-only tools, no project instruction file | search results, then only the ranges it needs | `<path>:<line>` pointers and one `FOUND`, `NOT FOUND` or `INCOMPLETE` line |
| `workflow:verify-item` | sonnet, medium, 20 turns, read-only tools | one item and the code it points at | one verdict: `SHIPPED`, `DECISION`, `REAL` or `CANNOT TELL`, with the write set a lane needs |

The brief that `dispatch --apply` writes names the `lane` agent on a launch line and repeats its model and effort there (`cd <lane folder> && claude --agent lane --model <model> --effort <effort>`), read from `agents/lane.md` at dispatch time so the brief cannot state a model the definition does not. The flags are on the line rather than left to the client to read from the definition. `claude --help` lists `--agent`, `--model` and `--effort` on Claude Code 2.1.92 (run on 2026-09-20); a client whose help does not is told by the brief to open a session in the lane folder and ask for the agent by name.

A lane's model may be overridden per lane from the plan's heading; the brief records which model the plan named, and the launch line carries it when it is a bare token, falling back to the definition's model when the heading's value is a sentence. Whether a lane agent's peak context stays under the window on real work is measured per dispatch (area 04 batch 03, area 07 batch 02), not assumed.
