# Applicability signals match import-shaped code, not bare library names

Kind: Living. Decision entry.

- **ID:** 2026-09-23-applicability-signals-match-import-shape-bcbd
- **Status:** proposed
- **Date:** 2026-09-23

## Decision

`security applicability --propose` (lib/security-propose.mjs) matches every library-name signal only in an
import/require/dependency-line shape (a helper, `importLike(name)`, matching `require('name')`, `from 'name'`,
`import 'name'`, a manifest's `"name": "version"` line, Python `import name` / `from name import`, Ruby
`require 'name'` / `gem 'name'`, a Cargo `name = "..."` line, or `name::` namespace use), never a bare word
matched anywhere in a tracked file's text.

## Why

While building this proposal against Skilliton's own repository to compare it with the applicability decisions
already recorded there (N65's own acceptance criterion), the first version used bare-word patterns (`/express/i`,
`/flask/i`, and others) and produced a false "applies" for SG-ACCESS-CONTROL, SG-INPUT-INJECTION and
SG-SECURITY-LOGGING: "express" matched "EXPRESS OR IMPLIED" in LICENSE, and "regular expressions" in a lesson
entry's own prose. A signal that fires on an MIT license file is not a signal at all, so every library-name
pattern was rewritten to require code-shaped context.

## Alternatives rejected

- Word-boundary matching alone (`\bexpress\b`) was tried first; it does not help, since "express" and "expressions"
  are both whole words.
- Restricting the scan to source-file extensions (.js, .py, .rb, ...) was considered, but a manifest's dependency
  declaration lives in package.json (not a source extension), and prose describing the codebase's own libraries
  (which is legitimate evidence, e.g. mentioning child_process) can appear in any tracked file; excluding by
  extension would have thrown out real signal along with the false one.

## Risk

The import-shaped patterns can still miss a real dependency written in a form none of the ten idioms in
`importLike()` covers (a re-exported alias, a dynamic `require(variable)`, a build-tool-specific import syntax).
Missing a signal makes a control propose "does not apply" that should apply; the accept step still requires a
person's `--decided-by` label, so this is a false negative a person can override, not a silent gap in the
recorded decision. The proposal's own reason text always says which tracked files it read, so a reviewer can tell
whether the negative is real.

## Reversibility

Easy: `importLike()` and the `SIGNALS` patterns are the only place this lives; adding, loosening or removing a
pattern is a one-function change with no effect on the applicability decisions already recorded (the proposal file
is fully regenerated by every `--propose --apply`).

## Evidence

scripts/security-propose.test.mjs's first test asserts directly that a tracked LICENSE file's "EXPRESS OR IMPLIED"
and a tracked notes file's "regular expressions" and "flask shape of a river" do not trigger the web-framework
signal, while `require('express')` in a tracked server.js does. Running `node scripts/skilliton.mjs security
applicability --propose --dir .` against this repository (recorded in LANE_REPORT.md) shows the proposal agrees
with the decisions already recorded in .skilliton/security/applicability.json for 12 of 15 controls (all 8
always-applying ones, plus 4 of the 7 signal-driven ones), with the three differences (SG-ACCESS-CONTROL,
SG-INPUT-INJECTION, SG-SECURITY-LOGGING) named and reasoned about rather than hidden inside a noisy
false-positive: this repository's own risk there runs through a git-based policy gate and hook/config parsing,
not through a web framework this proposal's signals look for.
