# Supported clients: what each one actually does

Kind: Living. **The rule this file exists to hold: a client is supported only when this matrix carries a column for it with at least one measured row. A client named anywhere else in this repository without such a column is documented or unverified, and is never described as supported.** `scripts/docs.test.mjs` fails when README.md names a client this matrix does not carry; the measured half is read here, by a person. Each row says how it is known: **measured** (a command or session run here, with the evidence file), **documented** (the client's official documentation or published source, not yet run here), or **unverified**. Versions matter: a row holds for the version named until it is measured again. Updated 2026-09-20. The third column is the Claude Code extension for VS Code, measured in one real session on 2026-09-20 (`evidence/live/2026-09-20-vs-code-extension-session.md`), which is why several of its cells read "not settled" rather than "no": the plugins on that machine were installed about 59 hours after that session began, so a plugin hook that did not fire is not evidence against the client. The fourth column is Cursor, and **every cell in it was read from Cursor's published documentation on 2026-09-20 with the page's URL in the cell; no session has ever been run there, so no Cursor cell says measured and Cursor is not a supported client.** A Cursor row with no documentation behind it says "not documented" rather than borrowing another client's behavior. Rows dated 2026-09-18 were measured on Claude Code 2.1.276, the editor-bundled binary; the rest on 2.1.273. Rows measured before milestone M9 (the rename, 2026-09-17) ran the same files under the earlier Skillgate names; the fork, machine and company release rehearsals were run again under the current names on the same client versions.

## What this means for a team

- **Claude Code** is the client whose lifecycle hooks Skilliton currently proves: the session-start project state, the stop reminder to record a checkpoint, and the guardrails block.
- **Codex CLI** receives the same skills (from the plugin) and instructions (`AGENTS.md`), and its hooks use the same shapes, but hooks cannot ship inside a Codex plugin in the measured version: a team configures them in a Codex configuration layer, and every hook needs a person to trust it once. The guardrails confirmation becomes a refusal. Codex lifecycle hooks stay unverified until a run from a logged-in, isolated Codex home records them (`scripts/rehearsals/live-clients.mjs --codex-home`).
- **Codex in the IDE** gets `AGENTS.md` and repository skills (`.agents/skills`) but no plugins, so no hooks and no `skilliton` launcher from a plugin.
- **Cursor** is not supported, because nothing in its column was run here. What its documentation says is worth knowing anyway: it reads `AGENTS.md` at the root and in subdirectories, so the harness block already reaches it; it reads skills from `.agents/skills/`, the same folder Skilliton already writes for Codex in the IDE; and unlike Codex it does carry hooks inside a plugin. Two things do not carry across: the hook event names and their JSON are Cursor's own, not Claude Code's, and there is no event whose output becomes prompt context, so the dispatch suggestion has no route there. See the decision entry `docs/decisions/2026-09-20-what-cursor-reads-and-what-a-skilliton-a-006f.md` for what an adapter would have to write.
