# IT allow list: what Skilliton needs on a developer's machine

Kind: Living. For IT and security teams rolling Skilliton out on managed laptops that run endpoint security: application allowlisting and ringfencing (for example ThreatLocker), endpoint detection and response, and proxies that inspect encrypted traffic. It lists every program Skilliton starts, every place it writes, what it reads outside a repository, its network use and its privileges, so rules can be written before rollout instead of after something silently stops working.

**How this list is known.** It is read from the code of the base plugins (`packs/base/plugins/`), `scripts/skilliton.mjs`, `scripts/setup.mjs` and `scripts/scrub-check.sh`; section 9 names the files each item comes from. `node scripts/allowlist.test.mjs` keeps it matched: it reads every program the code starts, every place the code reaches outside a repository, and every path a scenario writes in an empty home folder, and fails when this page does not say so (it runs in this repository's checks). **It has not been tested under any endpoint-security product** (docs/BACKLOG.md B29). `skilliton preflight` runs this list on a laptop and names anything blocked before setup changes anything. Platforms: macOS and Linux, measured. Windows is supported through Git for Windows and has not been measured yet (section 8).

## The short version

Each of these four is kept true by `node scripts/footprint.test.mjs`, which reads the code and fails when one of them stops holding.

- **User-level only.** After IT places its managed files, Skilliton needs no administrator rights. It never uses sudo, never writes to system folders, and installs no services, daemons, launch agents, scheduled tasks or login items.
- **No executables of its own, nothing downloaded to run.** Skilliton is scripts: JavaScript run by `node` and shell scripts run by `bash`, installed as plugin files by Claude Code or Codex.
- **One network command, and it is a check.** The runtime contains no network code. One command asks `git` to contact a remote: `skilliton preflight` (which `skilliton join` runs first) runs `git ls-remote` against the company's plugin repository to see whether this machine can reach it. Nothing else: no `git fetch`, `clone` or `push`. The rest of the network traffic comes from the AI tools themselves, including when they clone the company's plugin repository from GitHub.
- **Nothing keeps running.** Hooks and commands exit when done. The one exception is a test command defined by a project's own delivery policy that starts a background process of its own.

## 1. Programs to allow

| Program | Started by | When | If it is blocked |
|---|---|---|---|
| `claude` (Claude Code) and `codex` (Codex CLI) | The developer; `skilliton join` runs `plugin marketplace add` and `plugin install` (or `plugin add`); `skilliton doctor` runs `--version` and `plugin list --json`, including the `claude` binary bundled in VS Code, Cursor and Windsurf extensions | Setup, and every session | Nothing works; these are the tools Skilliton extends |
| `node` (22 or later) | The Claude Code hooks through `bin/skilliton`; the context-hygiene read guard (`hooks/read-guard.mjs`, a Node script started by its first line); the guardrails lane write guard (`hooks/lane-write-guard.mjs`, likewise) and managed block guard (`hooks/managed-block-guard.mjs`, likewise); every `skilliton` command; the terminal launcher; the pre-push hook `skilliton audit install --pre-push` writes, which runs `skilliton audit` on the range the push carries; and `skilliton usage`, which starts a second `node` to run the project's own meter (`scripts/token-cost.mjs`) and, before it prints any number from it, the test beside that meter | Every session start (which, on a machine that has joined, writes into a repository that is not prepared exactly the files `prepare --apply` writes, applies a pending instruction migration the way `migrate --apply` does, and leaves them uncommitted), stop, compaction and session end; on every prompt the person submits (the dispatch suggestion, which reads the prompt and stops there when it does not look like a list of tasks); before every file the AI reads with its Read tool (read guard); on every `git push` from a repository where that hook is installed; and every command | Session-start project state, checkpoint reminders and every command stop; a hook that fails prints a notice and never blocks the session because of its own failure; without the read guard, large whole-file reads are only instructed against |
| `bash`, `/usr/bin/env`, `/bin/sh` | Claude Code passes each hook command to a shell (`sh -c` on macOS and Linux, documented 2026-09-17 at https://code.claude.com/docs/en/hooks); every hook script starts with `#!/usr/bin/env bash`; the `~/.local/bin/skilliton` launcher is `/bin/sh` | Every session event, and before every shell command the AI runs (guardrails) | Hooks do not run; guardrails protection is off |
| `git` | Hooks (read-only: `rev-parse`, `symbolic-ref`, `status`, `log`, `rev-list`; guardrails adds `diff --cached` and `ls-files` when a command mentions git); commands (`verify-tag`, `verify-commit`, `tag -s` for signing releases, `config`, `archive`, and `ls-remote` in the preflight check). Every call passes `-c core.fsmonitor=false`, so a repository's own configuration cannot make git start another program | Every session event; before git commands the AI runs | Project state, guardrails' secret check on commits, release verification |
| `ssh-keygen` | `git` itself, to verify release signatures (`ssh-keygen -Y verify`) and, for release maintainers only, to sign (`ssh-keygen -Y sign`) | `skilliton verify`, `join`, release commands | `verify` cannot report VERIFIED |
| A JSON reader: `jq`, else `node`, else `python3`; on macOS also `/usr/bin/xcode-select` | The guardrails and handoff hooks, first one found; `xcode-select -p` only checks whether `python3` is the developer-tools stub | Every session start; before every shell command the AI runs | The hook reports it could not read its input |
| `awk`, `grep`, `find`, `sed`, `tr`, `wc`, `cat`, `dirname`, `readlink`, `date`, `mkdir`, `head`, `tail`, `cut`, `ls`, `xargs`, `tar` | Hook scripts; `tar` only in the delivery gate; `xargs` only in the scrub check used by `import` and `propose` | As above | The affected hook reports a problem |
| `cp`, `mktemp`, `rm` | Only the scrub check's own `--self-test`, which builds a throwaway folder and repository; `import` and `propose` do not reach it | When a maintainer runs that self-test | The self-test says it could not run |
| Programs a project's delivery policy names (`.skilliton/delivery.json`, for example the test runner) | `skilliton security collect tests` and `skilliton gate` on the laptop; the delivery gate on the shared repository | When those commands run | Evidence collection or the gate reports the check as failed |
| `npm`, through `/bin/sh` | `skilliton gate` runs `npm run verify` when the project has no delivery policy but package.json has a verify script; a command given after `--cmd` runs through the shell the same way | When a developer or the assistant runs `skilliton gate` | The gate reports the check could not start |
| `cmd.exe` (Windows only) | `runProgram` in the workflow runtime, when the program to start is a `.cmd` or `.bat` file such as npm's `claude` launcher, which Node cannot start directly; it runs `cmd.exe /d /s /c` with that one file, and refuses a path or argument holding a character `cmd.exe` would interpret | `skilliton doctor` and `join` on Windows | Those commands report that the client could not be started |

**Process chains.** Hooks run as `claude` → shell → `bash` or `node` → `git` → `ssh-keygen`; the read guard is `claude` → shell → `/usr/bin/env` → `node` and starts nothing. `skilliton gate` is `node` → the policy's programs, or `node` → `/bin/sh` → `npm` (or the command given). A ringfencing policy that limits which programs an approved program may start has to allow these parent and child relationships.

**Updates.** Claude Code and Codex update themselves. A rule that trusts a program by its exact file hash breaks at each update; rules by signing publisher or install location survive updates, where the product supports them (confirm with the vendor).

**Plugin scripts move with each release.** The scripts are installed under `~/.claude/plugins/cache/<marketplace>/<plugin>/<version>/` (Claude Code) and `~/.codex/plugins/cache/...` (Codex). A policy that controls scripts must let `bash` and `node` run files from there, and the `<version>` folder changes with every company release.

## 2. Where it writes

**On the machine, in the developer's home folder:**

| Location | Written by | Contents and modes |
|---|---|---|
| `~/.claude/plugins/` (`known_marketplaces.json`, `installed_plugins.json`, `cache/`) and `enabledPlugins`, `extraKnownMarketplaces` in `~/.claude/settings.json` | Claude Code's own plugin commands, run by `join` | The company marketplace and installed plugins. Skilliton reads `installed_plugins.json` and never writes it: `doctor` reads it, and the session start compares it with the plugins a project enables so it can say that enrollment comes first when they are not installed for this user |
| `~/.codex/` (`config.toml` marketplaces, `plugins/cache/`) | Codex's own plugin commands, run by `join`; `join` creates `~/.codex` (0700) when missing | The same for Codex |
| `~/.config/skilliton/trust/<company>.allowed_signers` | `join`, `trust add` | Whom this laptop trusts to sign releases; folder 0700, file 0644 |
| `~/.config/skilliton/joined/<company>.json` | `join` | What `join` added, so `join --undo` removes exactly that; folder 0700, file 0600 |
| `~/.local/bin/skilliton` | `join` | The terminal command, mode 0755; `join` does not edit PATH or shell profiles |
| `~/.claude/backups/skilliton/` | Commands that change a file outside a repository | A copy taken before the change |
| `~/.claude/skilliton/usage-log.jsonl`, `~/.claude/skilliton/statusline-keys-seen.log`, and the `statusLine` key in `~/.claude/settings.json` | Only if the optional status line is set up with `scripts/setup.mjs --apply` | Appended at every status line refresh |
| `~/.claude/skilliton/read-guard.log` | The context-hygiene read guard, each time it refuses a read | One line per refusal: time, session, folder, file, size |

`skilliton preflight` tests each of the folders above by writing one file named `.skilliton-preflight-<12 hex digits>` (mode 0600) in it and removing it again straight away, because a permission bit does not say what a security product will allow. A folder that does not exist yet is created (mode 0700), tested and removed again, so a rule that allows the home folder but not `~/.claude` is reported rather than passed; a folder it created and could not remove, because something else wrote in it meanwhile, is named in its output. It creates nothing else, and an interrupted run takes its own file with it.

Claude Code's and Codex's own locations move when `CLAUDE_CONFIG_DIR` or `CODEX_HOME` is set. Skilliton's own locations move with `SKILLITON_TRUST_DIR`, `SKILLITON_JOIN_DIR` and `SKILLITON_BACKUPS`, the status line's with `SKILLITON_USAGE_LOG`, `SKILLITON_KEYS_LOG` and `SKILLITON_SETTINGS`, and the read guard's log with `SKILLITON_READ_GUARD_LOG`, honoured only when it names an absolute `.log` path that is not a symbolic link (its size limit with `SKILLITON_READ_LIMIT_KB`). The backups folder follows `SKILLITON_BACKUPS` only: it stays at `~/.claude/backups/skilliton/` even when `CLAUDE_CONFIG_DIR` points somewhere else.

**In each code repository:**

| Location | Written by | Contents and modes |
|---|---|---|
| `.git/skilliton/journal.jsonl` | The session hooks (start, compaction, end, stop when a reminder is due, and prompt submission when a dispatch suggestion is given) and `checkpoint` | One line per event: time, event, session, branch, commit, count of changed files, a fingerprint. The dispatch suggestion adds three counts and a flag saying the prompt was longer than the hook reads, and never the prompt itself |
| `.git/skilliton-backups/` | Every command that changes project files | Copies before the change; folders 0700, files 0600 |
| `.git/hooks/pre-push` and the git setting `skilliton.auditRuntime` | `skilliton audit install --pre-push --apply`, and nothing else | A short script that runs `skilliton audit --pre-push`, mode 0755. It reports and never rejects a push. It is refused when `core.hooksPath` is set or when a pre-push hook this command did not write is already there, and a hook it replaces is kept under `~/.claude/backups/skilliton/` |
| `.git/skilliton/gate/<label>.log` (in a linked worktree, under its own `.git/worktrees/<name>/`) | `skilliton gate` | The full output of the checks it ran and the tree they ran on; folder 0700, file 0600 |
| `docs/` records, `CLAUDE.md`, `AGENTS.md`, `.gitignore`, `.claude/settings.json`, `.skilliton/` | `prepare`, `migrate`, `task`, `record`, `index`, `harness`, `project-settings`, `security` | Ordinary project files, reviewed and committed like code; `.claude/settings.json` carries the company marketplace, the enabled plugins, `autoCompactWindow`, `bashOutputMaxChars` and `taskOutputMaxChars` (docs/CONTRACTS.md section 5), nothing else; `.skilliton/private-evidence/` is 0700 with files 0600 and ignored by Git; `.skilliton/prepare.lock` is 0600 |

**Elsewhere, and not on most laptops:** the company skills repository (maintainers: `packs/`, `releases/`, `proposals/`, signed tags) and a shared repository's server (the delivery gate writes `hooks/pre-receive`, mode 0755, and two git settings; on GitHub the gate is an Actions workflow instead).

## 3. What it reads outside a repository

- **The AI tools' configuration:** Claude Code's plugin records and settings, whether `~/.claude.json` exists, and Codex's `config.toml`. `verify` reads and hashes every file of each installed plugin, to compare it with the signed release.
- **Editor extension folders:** `~/.vscode`, `~/.vscode-insiders`, `~/.cursor` and `~/.windsurf` extensions, where `doctor` looks for bundled Claude Code versions.
- **Its own folders:** `~/.config/skilliton/`, and the signers file IT provides.
- **What the hooks are given:** the guardrails hook receives the full text of every shell command the AI is about to run; session hooks receive the session ID and folder; the dispatch-suggestion hook receives the full text of every prompt the person submits, counts its items in memory and writes only those counts, never the text; the optional status line receives model, cost and usage figures.
- **Only when run by hand:** `config-drift-check.sh` reads the `model` and `version` fields of the newest Claude Code transcript. `skilliton usage` starts the project's own meter, which reads every Claude Code transcript under `~/.claude/projects/` (or `CLAUDE_CONFIG_DIR`) to count tokens; it sends nothing anywhere and writes nothing, and the numbers it reports are a reconstruction from those files rather than a bill.
- **Environment:** the `SKILLITON_*` settings, `CLAUDE_CONFIG_DIR`, `CODEX_HOME`, `CLAUDE_PLUGIN_ROOT`, `HOME`, `PATH`, `TMPDIR` and `LANG`. It lists environment variable names (not values) to report leftovers from the product's earlier name. Child programs (`git`, `claude`, `codex`, a policy's test command) receive the full environment; the delivery gate's checks receive only `PATH`, a temporary `HOME` and `LANG`.

## 4. Network

- **Skilliton's code:** no HTTP, socket or DNS code of its own. One `git` command contacts a remote: `git ls-remote --heads https://github.com/<owner>/<repo>` in `skilliton preflight`, run with prompts turned off (`GIT_TERMINAL_PROMPT=0`), to report whether the company's plugin repository can be reached from this machine. `skilliton join` runs that check before it changes anything. No other `git` command in the runtime contacts a remote.
- **The company plugin repository:** `claude plugin marketplace add <owner>/<repo>` and Codex's equivalent clone `https://github.com/<owner>/<repo>`, and later refresh it when auto-update is on. Allow HTTPS git traffic to `github.com` for Claude Code, Codex and `git`. A private repository uses each developer's GitHub credentials through git's credential helpers; that path is not yet tested (B31).
- **The AI tools' own traffic:** each vendor documents its required destinations. Claude Code's list, retrieved 2026-09-17, is at https://code.claude.com/docs/en/network-config and includes `api.anthropic.com`, `claude.ai`, `platform.claude.com`, `downloads.claude.ai` (installer and updates), `registry.npmjs.org` (npm installs of Claude Code and plugins' package dependencies; Skilliton's plugins declare none) and optional telemetry hosts. For Codex, see OpenAI's documentation (not retrieved here).
- **Proxies that inspect encrypted traffic:** Claude Code documents `HTTPS_PROXY`, `NODE_EXTRA_CA_CERTS` and client certificate settings on the page above. `git` needs the company certificate authority too (its system trust store or `http.sslCAInfo`). Skilliton's own `node` process makes no requests, so it needs no proxy settings.
- **A project's tests:** commands named in a delivery policy may use the network, as the project's tests normally do.

## 5. Privileges

- **Administrator rights:** needed only for IT's own managed files. Claude Code documents managed settings at `/Library/Application Support/ClaudeCode/` on macOS, `/etc/claude-code/` on Linux and `C:\Program Files\ClaudeCode\` on Windows, or as a macOS configuration profile or Windows `HKLM` registry value; Codex has its own managed files (docs/PHASE-3.md). Skilliton itself needs none.
- **Not used:** sudo, setuid or setgid, changing file ownership, system folders, services, launch agents, cron or systemd units, login items. File modes are set only on files Skilliton creates.
- **Signals:** it stops only the process groups it started (a policy's test command, on timeout or interruption).

## 6. What security software may notice, and why it is expected

1. **A hook reads every shell command before it runs.** Guardrails inspects each command the AI proposes, can block it or ask for confirmation, and for `git add` and `git commit` reads the staged changes to look for secrets.
2. **`node` and `git` run at every session event, and `node` on every prompt** and append to `.git/skilliton/journal.jsonl`. The stop hook can ask the AI to record a checkpoint before stopping. The prompt hook counts the items in a prompt and, at six or more, suggests splitting the work; it records the counts, never the prompt, and it cannot block or change a prompt.
3. **Other programs' settings files and instruction files are changed:** Claude Code and Codex plugin settings (through their own commands), a project's `.claude/settings.json`, `CLAUDE.md` and `AGENTS.md` (which AI tools read as instructions), and optionally the Claude Code status line setting. Each change is previewed first and backed up.
4. **An executable file is placed on PATH:** `~/.local/bin/skilliton`, and Claude Code puts the workflow plugin's `bin/` on the AI's shell PATH.
5. **Other command-line tools are driven to install software:** `join` runs `claude` and `codex` plugin commands.
6. **Signature checks with `ssh-keygen`**, started by `git verify-tag` and `git verify-commit`.
7. **Secret-shaped text in the source.** The secret checks contain patterns such as `sk-ant-`, `ghp_`, `AKIA` and private key headers, which a scanner may report as secrets. They are patterns, not credentials.
8. **File patterns:** temporary files created exclusively and renamed into place, security records published by hard link, and writes inside `.git/`.
9. **Scripts supplied by a repository:** `import` and `propose` run the company skills repository's own `scripts/scrub-check.sh`.

## 7. Guidance by kind of product

This is general guidance derived from the lists above. It has not been tested with any product (B29), so confirm each rule type with your vendor.

- **Application allowlisting (default deny):** allow the programs in section 1, by publisher or install location where possible. Allow `bash` and `node` to run scripts from the plugin cache folders, including new version folders. Allow `node` for the launcher at `~/.local/bin/skilliton`.
- **Ringfencing or containment:** allow the process chains in section 1, writes to the locations in section 2, and network access for `claude`, `codex` and `git` to the destinations in section 4. `node`, when running Skilliton, needs no network.
- **Endpoint detection and response:** expect the behaviors in section 6. Prefer narrow rules for these programs, paths and parent processes over broad exclusions.
- **Inspecting proxies:** give Claude Code and `git` the company certificate authority, and allow `github.com` for the company plugin repository.
- **When something is blocked:** a hook that fails prints a notice and never blocks the session because of its own failure (guardrails still blocks the commands it is meant to block), so a blocked program shows up as a missing project state or a guardrails notice rather than an error dialog. `skilliton verify` and `skilliton doctor` report installs and client versions they can read. `skilliton preflight` names each blocked item directly, with what to allow, and `skilliton join` runs it before it changes anything.

## 8. Known gaps

- Not tested under any endpoint-security product (B29). `skilliton preflight` reports what this machine did on this run; it does not say a product is supported.
- The preflight check does not start Claude Code or Codex: starting a coding tool writes into its own folder, and `join` promises that a preview changes nothing. So a policy that lets the tool's file be found but stops it starting is not caught before setup; it shows up when the tool is next run.
- A preflight run says which copy of the runtime it ran from. Only a run from the installed plugin exercises the plugin cache folder (`~/.claude/plugins/cache/...`) that a script policy has to allow; a run from a clone of the skills repository, which is how the first run happens, tests that clone's folder.
- A program that never returns is reported as not checked rather than as blocked, and the check moves on: it is stopped with its own process group, and the run says so. A program that puts a child of its own **outside** that group (`setsid`) cannot be stopped by anything Skilliton does; the check says that too, and that child may still be running afterwards.
- Every git command the runtime makes is run with the settings a repository or the environment could otherwise hand it removed: no repository configuration for the reachability check (it runs with `GIT_DIR` pointing at an empty folder), the `ext` transport refused, and `GIT_CONFIG`, `GIT_CONFIG_GLOBAL`, `GIT_CONFIG_SYSTEM`, `GIT_CONFIG_COUNT` and its keys, `GIT_PROXY_COMMAND`, `GIT_SSH_COMMAND`, `GIT_ALLOW_PROTOCOL`, `GIT_EXTERNAL_DIFF`, `GIT_TEXTCONV` and `GIT_EXEC_PATH` taken out of the environment, together with the variables that name a program for git to run for a person (`GIT_ASKPASS`, `SSH_ASKPASS`, `GIT_EDITOR`, `GIT_PAGER`, `GIT_TEMPLATE_DIR`), the ones that decide whether the certificate on the other end is checked (`GIT_SSL_NO_VERIFY`, `GIT_SSL_CAINFO` and the rest), and the ones that would name a different repository (`GIT_DIR`, `GIT_INDEX_FILE` and the rest), so that what a check reports is the repository it was pointed at. A copied working folder carries its own `.git/config`, and that file can rewrite an address and name a command to run for it; a prepared project's settings file can put variables into a session's environment, which is the same thing by another route. The guardrails hook takes the same variables out of its own git calls, using the shell's own `unset` so that it needs no program to do it.
- `BASH_ENV`, `SHELLOPTS` and a shell function exported into the environment are not in that list and cannot be, and they are worse than `PATH`. Bash runs the file `BASH_ENV` names, applies the options `SHELLOPTS` names, and imports any exported function, all before the first line of any script it starts. A file that says `exit 0`, or `SHELLOPTS=noexec` or `onecmd`, therefore ends a hook before it begins: the client sees no output and reads that as an allow. An exported function is subtler, because it replaces a program the hook uses inside the hook's own shell (measured: an exported `printf` turns a refusal into silence). The check is not steered, it is silenced. The guardrails hook asks for confirmation when it sees `BASH_ENV` set or a function imported, which catches the careless cases and not a deliberate one; `SHELLOPTS=noexec` cannot be reported at all, because no line of the hook runs. All of them are measured in `scripts/guardrails.test.sh`, including the two that cannot be defended, so they stay written-down facts. `ENV` is not in this class: only an interactive shell reads it, and a hook is a script (measured on bash, sh and dash). If your machines are managed, this is worth a line in whatever sets a developer's environment: nothing should be setting `BASH_ENV` or `SHELLOPTS`, or exporting shell functions.
- `PATH` is not in that list and cannot be: it is how any program on this machine is found, including `git` itself. A machine where something can put a program earlier on `PATH` than git is a machine where every tool is already affected, Skilliton among them. What the list above is for is the narrower case of a folder or a project's settings steering git while `PATH` is untouched.
- The one command that reaches a network, the reachability check, also takes its home folder from the system's record of this user rather than from `HOME`, and ignores `XDG_CONFIG_HOME`. `HOME` chooses `~/.gitconfig`, and that file can rewrite an address and name a program to run for it, so on that one call the configuration that applies is the one in the home folder the system records for this user. Where the system has no record (a container started with an unknown user id), or where `HOME` in the session is a different folder (a container, a CI runner, `sudo -u`), the check says so in its own line, naming both, so a "blocked" that comes from a configuration it declined to read can be read as that rather than taken to IT. What this machine's own `~/.gitconfig` and `/etc/gitconfig` say is followed on purpose: the company proxy and certificate live there, and the clone this check is a promise about would use them too. That same call also drops `GIT_CONFIG_NOSYSTEM` and `GIT_ATTR_NOSYSTEM`, because switching `/etc/gitconfig` off is the same act as redirecting it and would make a working machine report itself as blocked. Those two are the only variables treated differently on that call, and they are left in place on a local read for one reason: every test in this repository sets `GIT_CONFIG_NOSYSTEM` to isolate itself from the machine it runs on.
- A proxy named in the environment (`HTTPS_PROXY` and the rest) is followed, because that is how a company machine is set up and the check exists to answer whether this machine reaches the repository as it is set up. It is named in the check's own line, so an answer that came through a proxy says so instead of reading as an answer from github.com. The certificate is checked in every case: a proxy that answers as github.com with its own certificate is reported as blocked, with the certificate error, and not as reachable.
- The matching test's two rows about Claude Code's and Codex's own folders are exercised by stand-in clients written to match this page, so that pair is a check of the stand-in, not of the real tools; the enrollment rehearsal measures the real ones. The words of this page are not checked either, only the facts a reader can compare with the code.
- What the matching test covers, and what it does not: it reads the code, so a program started from a string built at run time, or by a program Skilliton starts (git starting `ssh-keygen`, a client updating itself), is named in this page by hand and not by measurement. The writes scenario measures the paths a run leaves in an empty home folder; a temporary file created and removed inside one step is not in that list.
- **Windows:** not supported yet. A hosted Windows runner has run the first steps (evidence/live/windows/): prepare, status and the session hooks work there since workflow 0.22.0. On Windows only, `runProgram` starts a `.cmd` or `.bat` file (npm's `claude` launcher) through `cmd.exe /d /s /c`, and only when neither its path nor any argument holds a character `cmd.exe` would read. The steps for the first run are docs/WINDOWS.md (B30). Claude Code hands each hook command to Git Bash on Windows, and to PowerShell when Git Bash is not installed (documented 2026-09-17 at https://code.claude.com/docs/en/hooks); every Skilliton hook now says `"shell": "bash"`, so a machine without Git Bash fails loudly instead of running a shell script under PowerShell. Node.js has to be installed separately there: the native Windows install of Claude Code does not bring it. Nothing on Windows has been measured; the first run on a Windows machine is what will say whether this holds. A private company repository is not tested (B31).
- Closed since this list was written: every git call the runtime makes now passes `-c core.fsmonitor=false`, so a copied repository whose own `.git/config` names a program cannot have it started by a session hook, `status`, `prepare`, the security collectors or the delivery gate (B33; `scripts/git-config.test.mjs`, whose first case proves plain git in the same repository does start it).

## 9. Where each item comes from

Paths are relative to `packs/base/plugins/` unless they start with `scripts/`.

- **Hook registrations:** `workflow/hooks/hooks.json`, `guardrails/hooks/hooks.json`, `context-hygiene/hooks/hooks.json`.

- **The preflight check:** `workflow/runtime/lib/preflight.mjs` (the table of programs, the folders, the repository check) and `workflow/runtime/preflight/probe.sh` (the script that starts the programs a hook uses, run by its path).
- **Programs started by the runtime:** `git` through `workflow/runtime/lib/journal.mjs`, `trust.mjs`, `collectors.mjs`, `delivery.mjs`, `core.mjs` and `prepare.mjs`; the policy's checks, `npm run verify` or the given command in `gate.mjs`; `claude` and `codex` in `workflow/runtime/lib/join.mjs`, `lib/doctor.mjs` and `commands/doctor.mjs`; signature checks in `trust.mjs` and `delivery.mjs`; signing in `workflow/runtime/commands/release.mjs`; the scrub check in `commands/import.mjs` and `commands/propose.mjs`; policy commands in `collectors.mjs` and `delivery.mjs`.

- **No network code:** a search of the plugins for HTTP, socket, DNS, `fetch`, `curl` and `wget` finds none, and no runtime `git` call contacts a remote. `scripts/allowlist.test.mjs` fails when one appears.
- **The matching test:** `scripts/allowlist.test.mjs` (with `scripts/inventory.mjs`, which reads the shell and JavaScript code), and `scripts/footprint.test.mjs` for the four promises in the short version. Each has a `--self-test` that proves its checks fail on known-bad input. What an interpreter is given is read too: a file a script hands to `bash`, `sh`, `node`, `python3` or `awk` has to be a file those tests read; a program written into a script is read for whether it starts a command of its own; `find -exec` is read as the command it is; and a command left running in the background, or a child started with options this reader cannot see, fails the check rather than passing quietly.
