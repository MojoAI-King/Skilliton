## Product outcome

A technical or nontechnical contributor can join a prepared repository, describe a task normally, build through the team's workflow, preserve decisions and progress, understand security gaps, submit a reviewable change, resume after interruption, and receive company-approved improvements without manually copying skills or rebuilding their setup.

## Implement the complete path

### 1. Repository preparation

Integrate the preparation/security foundation into the existing CLI and plugins. Adopt existing documents, provision missing records, preserve human content, and make repeat setup safe. Use one configuration contract and one managed instruction writer. Reconcile doctor, operation results, runtime identity, version requirements and prototype migrations with the target contracts.

### 2. Everyday workflow and continuity

Connect preparation, task tracking, checkpoints, Maintain, Review and Handoff. Verify supported lifecycle triggers rather than relying only on instructions. Support single-task work and parallel contributors without overwriting shared records. Prove recovery from actual durable state, including visibly missing or stale information.

### 3. Approved improvements and updates

Implement and demonstrate this flow:

`lesson -> proposed improvement -> regression/behavior tests -> company review and approved release -> package update -> versioned repository migration`

Separate executable package updates, project-record migrations and application changes. Prove exact approved version verification, tamper detection, recovery, rollback and removal while preserving project history. A native plugin update is not itself company approval or a completed repository migration.

### 4. Security and shared delivery

Integrate scoped framework mappings, applicability, supporting evidence, freshness and deduplicated backlog findings. Preserve missing, stale, invalid and needs-human states. Keep skill evaluation evidence separate from project security evidence. Broaden catalogs using reviewed versioned sources and appropriate permissions for restricted material.

Prove that trusted application checks reject a defective combined change. Local assistant guardrails and current evidence records must not substitute for merge enforcement or be presented as compliance certification. Security assessment preparation does not authorize active penetration testing; any active testing needs its own authorized scope.

### 5. End-to-end rehearsal

Exercise a fresh project, adoption of an existing project, interrupted-session recovery, two contributors, an approved skill improvement, a safe project migration, stale evidence and a blocked defective change. Include the security-review cases retained in PLAN.md.

Verify Claude Code and Codex separately through their actual supported mechanisms. Include the new-builder rehearsal required by M5. An agent simulating a beginner does not count as observed beginner usability. Record interventions, reviewer effort, integration repairs and missed requirements rather than declaring success from a green package test alone.

## Coordinate and execute

Establish one integrating session. Agree shared interfaces and assign bounded, non-overlapping write sets before parallel implementation. Preserve other sessions' work and keep task records durable. The integrating session owns shared plans/contracts, integration and final decision reconciliation.

Proceed autonomously through authorized implementation, local integration, fixes and disposable synthetic rehearsals. Keep advancing beyond the first milestone. Respect the current authorization boundaries for external actions and releases.

When an actual access, approval or human-participation dependency arises, request the smallest missing input and continue independent work. Keep the affected acceptance gate open. Historical usage-meter reproduction blocks savings claims, not core implementation.

Keep README, the one-pager, client instructions, contracts, decisions, milestone status and handoff synchronized with actual behavior. Retain passing and failing evidence, report skipped or unavailable checks explicitly, and tie results to the tested code. Follow the repository's test, review and public-content checks before committing.

## Completion

Finish with integrated code, a runnable demonstration, reproducible validation evidence, clear onboarding/update/recovery instructions, and exact commit and release status. Distinguish local, merged, published, installed and verified states.

Do not mark this goal complete while a required M1-M5 acceptance gate remains unverified. If progress requires a genuine external dependency, report the dependency and completed work accurately without substituting a simulated result or weakening the acceptance criterion.
