# Live check: the first real dispatch, two lanes, 2026-09-21

Kind: Reference. The first time `skilliton dispatch` was used for real work rather than in a fixture: two backlog items (B54 and B47) planned in `LANES.md`, one worktree and branch per lane, one lane agent each, both merged back to `main` the same evening. Everything below was read from the worktrees, the lane branches, the meter's own definition applied to the two lane transcripts, and this session's transcript. This file answers items 1 and 3 of docs/areas/07-dispatch-worktrees/batch-02-lane-agents-bounded.md and closes B38.

## The plan and the launch

`LANES.md` at the repository root (committed at 7ee1338): base commit 5b330f4, two lanes, model `sonnet`, context ceiling 120000 each. `dispatch --apply` created `../Skilliton-lanes/preview-before-write` on `lane/preview-0921` and `../Skilliton-lanes/apply-sweep-test` on `lane/sweep-0921`, wrote each `LANE_BRIEF.md`, and committed each lane's task record on its branch (`lane <name>: task record from LANES.md`, one acceptance criterion per item).

**On item 1's wording ("with the shipped agent definition").** The brief's launch line names the shipped `lane` agent (`packs/base/plugins/workflow/agents/lane.md`). In this session, run inside the Claude Code extension, that agent was not offered as a subagent type: the Agent tool lists the client's built-in types plus the user's own, and a plugin's agent was not among them (read from the tool's own list on 2026-09-21; whether a plugin agent reaches that list in a terminal session is unverified). Each lane was therefore launched as a `general-purpose` subagent on `sonnet` with the text of `lane.md` and the lane's brief pasted as its instructions. The definition ran; the launch route was not the brief's `--agent` line. The item is ticked on that reading and the batch note says so.

## The merge

Serial, on `main`: lane two merged first (22d98a7, no conflict), lane one rebased onto that result (five commits replayed cleanly) and merged (efb136a). `dispatch merge` in preview reported each lane's task record as brought back and the integration branch's own task record as a conflict (each lane carried the base copy; `main`'s had moved on), which is the right call and needed nothing. The records came over with the git merges themselves.

**The full suite on the merged tree found one thing the lanes could not:** `scripts/demo-day.mjs` and three rehearsal scripts called `new-skill` and `import` without `--apply`, so the preview lane's change turned them into previews and demo-day failed (56 of 57 steps; scratchpad suite13.out). Each lane's own test file passed because none of those callers is in it. Fixed on `main` by adding `--apply` to the four callers and to the three guide examples; demo-day, docs, skilliton, lint, names, scrub, the projects rehearsal and the enrollment self-test all pass after the fix. Recorded as a lesson: a lane's test command is its own file, and the integrating session's gate is the full suite.

## What this proves, and what it does not

- Proves: the plan, the worktrees, the briefs, the committed task records, the lane guard, LANE DONE, the merge-back preview's three classes, and two lanes finishing real backlog items under a stated context ceiling, measured.
- Does not prove: a lane launched through the brief's `--agent` line (the plugin agent was not offered here); a lane on a machine other than this one; `dispatch merge --apply` writing records (the git merges brought them, so it had nothing to write).
- Found: `LANES.md` item IDs must be `N` followed by digits; items written as `P1.` and `S1.` were dropped from the plan without a word (B55). Two lane commits carried no co-author trailer; the merge commit records it.
